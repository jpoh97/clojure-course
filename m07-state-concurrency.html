State & Concurrency

Immutable values plus a small set of explicit reference types — atoms, refs (STM), agents — and channels for coordination.

Goals
  • Internalize identity-vs-value: references point to successive immutable values.
  • Pick the right reference type for each situation.
  • Use atoms safely (and understand why swap! functions must be pure).
  • Coordinate multi-step updates with software transactional memory.

The mental model that changes everything

In Java, an object's fields change in place while other threads may be reading them — hence locks, volatile, concurrent collections. Clojure separates the two concerns:

  • Values never change (Module 03).
  • Identities are named cells that point to successive values over time.
(def account (atom {:owner "ada" :balance 100}))
;; 'account' is the identity; each snapshot it points to is an immutable value.

@account                        ;=> {:owner "ada", :balance 100}   current value

(swap! account update :balance + 50)
@account                        ;=> {:owner "ada", :balance 150}

Atoms: your AtomicReference, but nicer

(def hits (atom 0))

(swap! hits inc)                 ; compare-and-swap loop under the hood
(swap! hits + 10)                ; apply any function to current value
(reset! hits 0)                  ; unconditional overwrite

;; swap! retries on contention - so the function must be PURE:
(swap! hits (fn [n] (inc n)))    ; good: no side effects inside

;; validation and observation:
(def port (atom 8080
           :validator #(or (nil? %) (pos? %))))     ; rejects invalid states
(add-watch hits :audit
           (fn [_key _ref old new]
             (println "hits:" old "->" new)))
(remove-watch hits :audit)
Classic bug

Never do side effects (logging, HTTP calls, DB writes) inside a swap!: contention causes retries, so your effect can run twice. Compute the new state purely, then perform effects outside — or reach for agents/channels which serialize effects exactly once.

Refs & STM: transactions across multiple identities

Sometimes one logical operation must touch several pieces of state atomically — the classic money transfer. Clojure ships a software transactional memory:

(def alice (ref 100))
(def bob   (ref 50))

(dosync
  (alter alice - 30)
  (alter bob   + 30))
;; both succeed or both roll back - no locks held across user code.

[@alice @bob]                    ;=> [70 80]

;; commute: order doesn't matter (e.g., adding to a set) - more concurrency:
(dosync (commute bob + 5))
Pragmatic reality check

STM is elegant but rare in application code. Most systems model shared state as one atom holding the whole world (a single map), updated transactionally by pure functions — this is precisely how re-frame manages all frontend state (Module 12). Reach for refs only when independent identities genuinely need coordinated commits.

Agents, vars, futures, promises

;; Agent: asynchronous, serialized updates - actions queue up.
(def logger (agent []))
(send logger conj "event-1")          ; runs later, once, on one thread
(send-off logger conj "blocking-io")  ; variant for blocking work
(await logger)                        ; wait until queued actions finish
@logger                               ;=> ["event-1" "blocking-io"]

;; Dynamic vars: thread-local context (like MDC / ThreadLocal).
(def ^:dynamic *request-id* nil)
(binding [*request-id* "abc-123"]
  (handle-request))

;; Futures & promises: one-shot concurrency primitives.
(def result (future (expensive-computation)))   ; starts immediately
(def ready  (promise))
(deliver ready {:ok true})
@ready

;; pmap: parallel map over expensive pure work.
(pmap #(fetch-url %) urls)

core.async: channels instead of callback pyramids

(require '[clojure.core.async :as a])

(def jobs (a/chan 10))                       ; buffered channel

;; three workers pulling from the same channel:
(dotimes [worker 3]
  (a/go-loop []
    (when-let [job (a/<! jobs)]              ; park (non-blocking wait)
      (process job)
      (recur))))

(a/go (a/>! jobs "task-a"))                  ; put from a go block
(a/thread (a/>!! jobs "task-b"))             ; blocking put off-thread

(a/close! jobs)

go blocks compile to a state machine — like Kotlin coroutines' suspension, though without structured cancellation. Channels give you queues, fan-out/fan-in, timeouts (a/timeout) and pipelines as first-class values.

Where this is used for real

Nubank credits Clojure's state model as a key reason their teams can evolve financial logic safely: business rules are pure transformations of immutable data, and mutation happens at explicit, audited boundaries. Rate limiters, caches and circuit breakers are typically a few lines around an atom.

Tasks

Task 1Race-safe ID generator. Create an atom-based generator returning sequential ids like "user-1", "user-2"… Call it from two threads and confirm no duplicates.
Solution 
(def next-id (atom 0))

(defn new-user-id []
  (str "user-" (swap! next-id inc)))

(new-user-id)   ;=> "user-1"
;; swap!'s CAS loop makes concurrent calls safe without locks.
Task 2Audited cache. Make an atom holding a map; add a watch that records every change into a second atom (key, old value, new value).
Solution 
(def cache (atom {}))
(def audit (atom []))

(add-watch cache :log
  (fn [_ _ k old new]
    (swap! audit conj {:key k :old old :new new})))

(swap! cache assoc "a" 1)
@audit   ;=> [{:key "a", :old {}, :new {"a" 1}}]
Task 3Atomic transfer. With two refs holding balances, write (transfer! from to amount) using dosync; make it throw when funds are insufficient so nothing changes at all.
Solution 
(defn transfer! [from to amount]
  (dosync
    (when (< @from amount)
      (throw (ex-info "insufficient funds" {:amount amount})))
    (alter from - amount)
    (alter to   + amount)))

(transfer! alice bob 20)   ; both refs update together or not at all
Task 4Worker pool. Set up a channel plus three go-loop workers that print each received item; push five items through and close the channel.
Solution 
(require '[clojure.core.async :as a])

(def ch (a/chan))
(dotimes [w 3]
  (a/go-loop []
    (when-let [x (a/<! ch)]
      (println "worker" w ":" x)
      (recur))))

(doseq [x (range 5)] (a/go (a/>! ch x)))
(Thread/sleep 500)         ; let go blocks drain (demo only)
(a/close! ch)

Exam · Module 07

1 · Which reference type covers most day-to-day application state?
Atoms handle uncoordinated synchronous updates - counters, caches, config, even entire app state as one map. Refs/agents cover special cases.
2 · Why must functions passed to swap! be pure?
Under contention the CAS loop re-runs the function against the latest value. Duplicate side effects would corrupt logs, HTTP calls, DB rows...
3 · What does (dosync ...) guarantee?
dosync wraps ref operations in an STM transaction - consistent snapshots, automatic retries on conflict.
4 · An agent differs from an atom because…
You enqueue actions; they execute later, one at a time, in submission order per agent - ideal for serialized background writes.
5 · In core.async, what is special about a/<! inside a go block?
Inside go blocks you use parking ops (>! <!) compiled into a state machine; on real threads you use blocking variants (>!! <!!).
