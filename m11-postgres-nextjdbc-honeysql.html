PostgreSQL: next.jdbc + HoneySQL

Your Postgres experience transfers completely. Clojure skips ORM magic and treats SQL — and the queries themselves — as data.

Goals
  • Connect to Postgres with pooling (yes, HikariCP again).
  • Run parameterized queries, inserts and transactions safely.
  • Build dynamic queries as data structures with HoneySQL.
  • Manage schema changes with migrations.

Datasources and your first queries

(ns shop.db
  (:require [next.jdbc :as jdbc]
            [next.jdbc.result-set :as rs]))

;; simple spec map - next.jdbc builds an embedded datasource:
(def ds (jdbc/get-datasource
          {:dbtype "postgresql" :host "localhost" :port 5432
           :dbname "shop" :username "postgres" :password "secret"}))

(jdbc/execute! ds ["select * from users"])
;=> [{:USERS/ID 1, :USERS/EMAIL "ada@x.io"}]
;;   ^ table-qualified keywords by default (schema-aware!)

;; usually you want plain keys:
(jdbc/execute-one! ds
  ["select id, email from users where id = ?" 1]
  {:builder-fn rs/as-unqualified-maps})
;=> {:id 1, :email "ada@x.io"}
  • ? placeholders are always parameterized — string concatenation of SQL is a code smell here just like anywhere.
  • execute! returns a vector of row maps (even for one row); execute-one! returns a single map or nil.

The production pool: HikariCP

(require '[hikari-cp.core :as hk])

(def ds (hk/make-datasource
          {:jdbc-url          "jdbc:postgresql://localhost:5432/shop"
           :username          "postgres"
           :password          "secret"
           :maximum-pool-size 10}))

(hk/close-datasource ds)   ; at shutdown

Writes, RETURNING and transactions

;; insert and read back generated columns:
(jdbc/execute-one! ds
  ["insert into users (email) values (?) returning id, email" "ada@x.io"]
  {:builder-fn rs/as-unqualified-maps})
;=> {:id 42, :email "ada@x.io"}

;; transactions - throw inside and everything rolls back:
(jdbc/with-transaction [tx ds {:isolation "repeatable-read"}]
  (jdbc/execute-one! tx ["update accounts set balance = balance - 50 where id = ?" 1])
  (jdbc/execute-one! tx ["update accounts set balance = balance + 50 where id = ?" 2]))

HoneySQL: queries as data

(require '[honey.sql :as sql])

(sql/format {:select   [:id :email]
             :from     [:users]
             :where    [:and [:= :status "active"] [:> :age 18]]
             :order-by [[:created-at :desc]]
             :limit    20})
;=> [["select id, email from users where status = ? and age > ? order by created_at desc limit 20"
;     "active" 18]]

;; writes are data too:
(sql/format {:insert-into :products
             :values      [{:name "Widget" :price 9.99}]})
(sql/format {:update :products :set {:price 12.50} :where [:= :id 7]})
(sql/format {:delete-from :sessions :where [:< :expires-at [:now]]})

The killer feature is composability: filters accumulate like any other data structure (Modules 03 and 05), so dynamic search endpoints stop being string-concatenation minefields:

(defn search-users [{:keys [email-like active? limit]}]
  (let [filters (cond-> []
                  email-like (conj [:like :email (str "%" email-like "%")])
                  active?    (conj [:= :active true]))]
    (-> {:select [:*] :from [:users]}
        (assoc :where (if (seq filters) (into [:and] filters) true))
        (assoc :limit (or limit 50))
        (as-> q (jdbc/execute! ds (sql/format q)
                                {:builder-fn rs/as-unqualified-maps})))))
SQL-first alternative

If you prefer writing raw SQL in files (MyBatis style), look at HugSQL: annotated -- :name find-by-email comments become real functions at compile time. Many teams mix both: HoneySQL for dynamic parts, hand-written SQL for complex reporting.

Fitting into the app (Module 10)

;; shop/db/users.clj - repository functions take ds explicitly:
(defn find-by-email [ds email]
  (jdbc/execute-one! ds ["select * from users where email = ?" email]
                     {:builder-fn rs/as-unqualified-maps}))

;; handlers receive ds via closure/partial - DI without annotations:
(defn make-handler [ds]
  (ring/router
    [["/api/users/by-email/:email"
      {:get (fn [req]
              (if-some [u (find-by-email ds (get-in req [:path-params :email]))]
                {:status 200 :body u}
                {:status 404 :body {:error "nope"}}))}]]))

;; JSONB roundtrip:
(jdbc/execute-one! ds ["insert into events (payload) values (?::jsonb)"
                        (json/generate-string {:kind "signup"})])
(jdbc/execute-one! ds ["select payload->>'kind' as kind from events limit 1"])
No Hibernate — on purpose

Clojure culture prefers explicit SQL over object-relational mapping: what runs is what you wrote, performance tuning is ordinary Postgres work, and there is no lazy-load/session state to debug. The tradeoff is manual result-to-map plumbing (thin, thanks to builders) and no change-tracking — updates are explicit statements.

Where this is used for real

Metabase, the open-source BI tool, is a giant Clojure application whose core is exactly this: next.jdbc-style connections to dozens of databases, queries composed as data. Nubank pairs Clojure services with Postgres/Datomic for ledger-scale correctness.

Task 1Connect and explore. Start the Docker container, define ds, and list all tables by querying information_schema.tables.
Solution

  ["select table_name from information_schema.tables where table_schema = 'public'"])
Task 2Products repository. Write create!, find-all, find-by-id, delete! for a products table using unqualified map results and RETURNING on insert.
Solution 
(defn create! [ds p]
  (jdbc/execute-one! ds
    ["insert into products (name, price) values (?, ?) returning id, name, price"
     (:name p) (:price p)]
    {:builder-fn rs/as-unqualified-maps}))

(defn find-all [ds]
  (jdbc/execute! ds ["select * from products order by id"]
                 {:builder-fn rs/as-unqualified-maps}))

(defn delete! [ds id]
  (jdbc/execute-one! ds ["delete from products where id = ?" id]))
Task 3Dynamic filter. Extend Task 2 with (search ds {:max-price 20 :name-like "wid"}) built with HoneySQL + cond->.
Solution 
(defn search [ds {:keys [max-price name-like]}]
  (let [f (cond-> []
            max-price (conj [:<= :price max-price])
            name-like (conj [:like :name (str "%" name-like "%")]))]
    (jdbc/execute! ds
      (sql/format (-> {:select [:*] :from [:products]}
                      (assoc :where (if (seq f) (into [:and] f) true))))
      {:builder-fn rs/as-unqualified-maps})))
Task 4Guarded stock transfer. In a transaction, move quantity from product A to B only if A has stock — otherwise roll back everything.
Solution 
(defn move-stock! [ds from-id to-id qty]
  (jdbc/with-transaction [tx ds]
    (let [{:keys [stock]} (jdbc/execute-one! tx
                            ["select stock from products where id = ? for update" from-id])]
      (when (< stock qty)
        (throw (ex-info "insufficient stock" {:qty qty})))
      (jdbc/execute-one! tx ["update products set stock = stock - ? where id = ?" qty from-id])
      (jdbc/execute-one! tx ["update products set stock = stock + ? where id = ?" qty to-id]))))

Summary · what you covered
  • Your stack translates: JPA/Hibernate → plain maps (or records); jOOQ/Exposed → HoneySQL; MyBatis → HugSQL; Flyway → Migratus/Ragtime; HikariCP is HikariCP.
  • Connect without ORM magic: next.jdbc reads a spec map, builds a datasource, runs parameterized SQL (execute!), rows come back as plain maps.
  • Row-key qualification: :USERS/ID avoids collisions across joins; opt out with result-set builder fns when unqualified keys suit.
  • HoneySQL builds SQL as data: conditional filters are just assoc/conj on a map; formatting always emits bound parameters — injection is impossible.
  • Transactions: jdbc/with-transaction rolls back the whole transaction on an exception and commits on normal completion.
  • Migrations: Migratus/Ragtime apply versioned scripts and record them — the same job Flyway does.

Exam · Module 11

1 · What does (jdbc/execute! ds ["select ... where id = ?" 42]) give you?
Results materialize as immutable maps; parameters are always bound server-side, neutralizing injection.
2 · Why does :USERS/ID appear instead of :ID?
Qualified keys prevent collisions across joins (two tables both having :id); as-unqualified-apache/as-unqualified-maps opt out when you don't need it.
3 · What is the main advantage of building queries with HoneySQL?
Dynamic filtering/search becomes assoc/conj on a map instead of fragile string concatenation, and formatting guarantees parameterization.
4 · Throwing an exception inside jdbc/with-transaction…
The macro wraps the body in try/catch: exception => rollback + rethrow; normal completion => commit.
5 · Which pairing matches Flyway's role in Spring projects?
Migratus/Ragtime apply versioned migration files and record them - the same job Flyway does. HikariCP is the pool itself (both worlds).
